# Decisions

Every decision we settle in discussion, recorded when it is made. The plan
([IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)) says what we set out to build; this file says
where we changed course, and why. Newest last. Both lanes append here.

**Status:** *done* is in the code; *agreed* is settled but not yet built.
**Contract decisions** (anything in `services/core/app/schemas/` or the n8n workflow table) need
both people, per [LANES.md](LANES.md) §2.

## Infrastructure (2A)

| # | Decision | Why | Agreed | Status |
|---|---|---|---|---|
| D17 | **`tasks.py` uses only the standard library** (`argparse`), not `invoke`. | It has to run on a fresh clone, on macOS and Windows, before any `pip install`. Every usage in the plan is already `python tasks.py …`. | A | done |
| D18 | **Postgres is `pgvector/pgvector:pg16`; Caddy is `caddy:2.10-alpine`; local n8n is `n8nio/n8n:2.39.7`.** | n8n matches the Cloud instance (0.1). The plan pinned neither of the others. | A | done |
| D19 | **B's services sit behind a compose profile (`surfaces`)**, so `tasks.py up` works before their Dockerfiles exist. Caddy returns 502 for `/mem/*` and the web root until they do. | A must not block on B, and B must not edit A's compose file. | A | done |
| D25 | **The db init script is `.sql`, not `.sh`.** | The `.sh` passed the entrypoint's `-x` check but failed from the bind mount with "bad interpreter". Postgres exited, restarted, skipped init, and `cognee` and `n8n-local` were never created, with no error surfaced by `tasks.py up`. The entrypoint pipes `.sql` through psql, so nothing needs an exec bit, which WSL2 (the demo laptop) preserves no better. | A | done |
| D26 | **Caddy's CORS allowlist takes one `header Origin` value per line.** | Two values on one line is invalid Caddyfile, and compose always sets `PUBLIC_URL`, so Caddy never started. The app is served same-origin through Caddy, so CORS only matters for a dev server on another port. | A | done |
| D27 | **`tasks.py generate` passes `--out` and `--force` through.** | Without them it could never regenerate over existing data. | A | done |
| D30 | **Cassette normalisation keeps an allowlist of headers (`content-type` only), not a denylist.** | The frozen format lists what to drop. Listing drops means a header nobody anticipated (a user agent, a new trace header) silently changes the request key and the cassette stops matching, which is only discovered when a paid recording turns out to be unusable. `accept` is excluded for the same reason: n8n, curl and the test client all send different ones. | A | done |
| D31 | **Twilio media bytes are not recorded.** Cassettes cover Sarvam calls and the Twilio Messages API. | A media URL carries SIDs generated by Twilio at record time and by the fakes at replay time, so the key could never match. The fakes already synthesise media deterministically (2F.6); what is worth paying for is what cannot be synthesised, which is all Sarvam. | A | done |
| D32 | **Recording requires `--live` and `HISAAB_LIVE=1`,** refused by `tasks.py` and again by the fakes at startup. Cassettes are bind-mounted out of the container. | Recording against the fakes would spend the window's budget and write cassettes of our own answers. Without the mount, recordings made in a live window would die with the container. | A | done |
| D33 | **`tasks.py snapshot` and `tasks.py reset` restore the demo database from a `pg_dump`.** Take the snapshot straight after `replay`, before any workflow run. | The ledger refuses UPDATE, DELETE and TRUNCATE, so there is no way back in place. A CP1 run that labels the demo credits cannot be undone, and WF10 skips credits that already carry a machine label: after one interrupted run, 67 of the window's 68 credits were labelled and CP1 could never again select three questions on that database. Restoring a dump is the only route back, so it became the blocker rather than a convenience. | A | done |
| D34 | **`GET /credits` takes a half-open `[from, to)` window**, both bounds aware instants, either one optional. A bare date is refused. | WF10 was paging all 12,097 credits through a Code node to keep the 68 in its window, so every page became a task-runner job over a large payload. On A's machine that starved the JS runner and the shared pg-pool: `not matched to a runner (waited 128 seconds)` and `timeout exceeded when trying to connect`, with runs at 1220 s and 1632 s against B's 117 s. Filtering in SQL turns roughly 61 pages into one. A bare date is refused because the chain stores UTC and the screens answer IST, and a window silently shifted by 5.5 hours is the same class of bug as the string comparison in `44b7af2`. | A, B | done |
| D35 | **A lien opens the freeze case; a decline burst is only recorded on it.** No case opens without a `lien_marked` event. When 3 or more `payment_declined` fall in the 30 minutes up to the lien, the burst is stored on the case and passed to WF20. | Plan §13 reads "a `lien_marked` event, **or** 3 or more declines within 30 minutes followed by lien confirmation", but both branches end at the lien, and `lien_marked` is the only lien event there is. A burst alone looks the same as a bank outage, and opening a case on one would tell a merchant their money is held when it is not. In the demo data the declines follow the lien (09:30 lien, first decline 09:41) because they are its consequence, so a late lien notice must not count them as warning: the burst is bounded above by the lien's own time. | A | done |
| D36 | **A freeze case is dated to the lien, opened by replay without starting WF20, and announced to WF20 only after it commits, on a best-effort basis.** | Replay loads events at its cutoff, so dating the case at ingest would move a 24 March freeze to whatever day the replay stopped, and every read before that would miss it. Replay loads history, and no other replayed record runs a workflow. By default FastAPI 0.141 runs background tasks before a yield dependency exits, which here is before COMMIT, so WF20 could ask about a case that did not exist yet; the route's connection uses `scope="function"`, which commits first, and a failed commit returns 500 with no webhook. A webhook failure does not roll back the case: a lien that reached the ledger is evidence and n8n is not, and WF20 polls for the decision anyway. Checked on the running stack: a probe standing in for WF20 found the case already committed when it was notified, and with n8n stopped the lien still returned 200 and opened the case. | A | done |
| D37 | **The outbox gate reads the ledger, never `ops.approvals`; an officer's decision is final.** `POST /outbox/{pack}/send` sends only when the chain holds a `pack.approved` for that pack by the officer role and no `pack.rejected`. A pack gets one decision: an identical retry returns the original entry, anything else is 409. Sends are idempotent per pack in the same way. | The application role may UPDATE ops working state, so a gate on a status column could be opened by editing one row; the ledger refuses UPDATE and DELETE. Final decisions mean a pack can never carry both an approval and a rejection, and the outbox still refuses if the ledger somehow held both. Retries return the original because n8n retries and phones double-tap. Decisions and sends take the merchant's chain lock first, like questions, so two officers cannot both see "no decision yet". | A | done |
| D38 | **Resuming WF20 happens after commit, only at our own n8n, and `workflow_resumed` means "scheduled".** | The resume must not reach the Wait before the decision is visible, or WF20 re-reads core and finds nothing; the decision routes therefore commit before their background task (the D36 mechanism). That leaves the response unable to report delivery, so `workflow_resumed: true` means a resume URL is stored and a resume will follow the commit. The call carries the webhook secret, so core only calls a URL on `N8N_BASE_URL`'s origin: a stored URL anywhere else is ignored. An identical retry resumes again, because the first attempt may have been lost and a Wait that already resumed ignores it. Resume URLs are stored with the pack; `POST /packs` takes one in 6.8. | A | done |
| D39 | **`ledger.current_view` takes an optional third argument, `p_opened_at timestamptz DEFAULT NULL`, and computes `tier` itself.** The tier is decided in one order: anything whose supporting entry was recorded at or after the case boundary, or whose latest claim is `claim.annotated`, is tier 4; else a `bill.linked` before the boundary agreeing with the effective label is tier 1; else a pre-boundary `claim.answered` is tier 3; else a pre-boundary `label.proposed` with no claim is tier 2; else NULL. | 6.1 asks for tiers in `current_view`, but the view has no case, and §6 defines tiers relative to a case's `opened_at`. A defaulted third argument keeps every existing two-argument caller (`projection.py`, `cases/build.py`, `ops/screens.py`) working unchanged while letting `skills/tiers.py` pass the boundary. Deciding the tier in SQL beside `effective_label` keeps the two from drifting: the tier is a statement about *which* entry produced that label, so computing it anywhere else means re-deriving the label. NULL rather than 4 for "no evidence at all" keeps "we have nothing" distinct from "they added it after the notice", which is the distinction the shape figure exists to make. | A | done |
| D40 | **Turnover splits billed sales by bill line and apportions only the unbilled ones.** Billed sales are split exactly, line by line, on `hsn_catalog.exempt`; unbilled sales are split at the shop's billed exempt share, by value, and disclosed in `estimated_unbilled_*`. `aggregate = taxable + exempt` holds exactly, because the taxable estimate is the unbilled total minus the exempt estimate rather than a second rounding. **With no billed sales in the period the share is 0.0 and every unbilled rupee is taxable.** | §5 asks for apportionment "by value from the shop's billed exempt share", which only describes the unbilled part; a bill that carries both exempt and taxable lines is not an estimate and must not be rounded into one by the credit's single `effective_label`. Subtracting one estimate from the total removes the drift where two independently rounded halves fail to sum to the whole, which a CA reading the workings would catch immediately. The 0.0 fallback is deliberately conservative: with no billed mix to reason from, the system must never quietly move money into the exempt column, which is the one direction that would help hide income. | A | done |
| D41 | **`coverage_fraction` is the share of the period's credit ₹ carrying a usable label, not the share backed by a bill**, and unclassified credits appear in `excluded` with "Not yet classified." | The billed share is already visible through `estimated_unbilled_*`, so spending the contract's one coverage field on it says nothing new. The bigger risk is money leaving turnover in silence: an unlabelled credit is neither a sale nor an excluded bucket, so without this it would simply not appear. Listing it and letting it pull coverage down means every rupee in the period is accounted for somewhere in the response. The billed share still appears as a workings line. | A | done |
| D42 | **Guards fail closed, and `numbers` ships with 6.6 rather than apart from `extraction`.** Both compare figures by numeric value through one shared parser; a four-digit number is only ignored when its context says year (`FY 2025-26`, a date, a time), never because of its digit count. Any unreadable or unparseable `legal/citations.yaml` blocks rather than passes. | The two guards ask the same question of different sources — does every figure in this text appear in that source — so two parsers would drift and the weaker one would decide. The digit-count rule is not hypothetical: the first draft skipped every bare four-digit number as a possible year, which waved through any invented figure from 1000 to 9999. The demo's own disputed payment is \u20b94,200, so the guard whose purpose is "the LLM never does arithmetic" was blind in exactly the range the demo turns on. Failing closed is the only safe default for a check standing between generated text and a bank or the police. | A | done |
| D43 | **A linked bill classifies a credit for turnover when nothing else has.** Precedence in `skills/turnover.py`: an explicit `effective_label` decides first, and only a credit whose label is NULL or `unclassified` falls back to its bill lines. Such a credit counts as classified, so it does not drag `coverage_fraction` down, and a workings line names how much turnover rests on a bill with no recorded label. | Found by running 6.2 against the real demo database rather than only its tests: it returned ₹0 turnover with all 12,097 credits excluded, because that database holds 4,125 `bill.linked` entries and zero `label.proposed` — WF10 had not run. `current_view` already computes `bill_label` for those rows, uses it for `conflict` and for tier 1, then discards it, since `effective_label` is only `coalesce(claim_label, machine_label)`. So the strongest evidence in the system was the one thing turnover ignored, while `classify_rules` treats an itemised bill as confidence 1.0 and §6 ranks a bill above a rule's own proposal. A tax pack showing ₹0 because a workflow has not run yet is not a figure a CA can use. The fallback is deliberately one-way: an explicit non-sale label still wins, so a bill can never resurrect money somebody already ruled out. | A | done |
| D44 | **The threshold projection is emitted only while it can still mean something:** the merchant is unregistered, not exclusively exempt, `aggregate_turnover` is at or below the threshold, and no ledger-derived `crossed_on` exists. Otherwise `trailing_60_day_run_rate`, `projected_crossing_on` and `warning_days` are all null. `crossed_on` stays evidence-backed: it is the day the ledger's own running total first went strictly above, and stays null when the ledger cannot support one, even if the caller's `aggregate_turnover` is above. | Probing the real demo database showed a merchant already ₹1,00,000 over the threshold being told it would cross on 15 February, five weeks before the as-of date. Extrapolating a negative remaining gap produces a date in the past, and clamping `warning_days` to 0 hid that rather than preventing it. Tying the projection to `crossed_on` was the original error: `crossed_on` answers what the ledger can prove, while the verdict answers on the figure the caller supplied, and the two legitimately disagree when the ledger holds only part of the year. A registered merchant, an exclusively-exempt supplier and a merchant already above the threshold are none of them approaching registration, so for all three the honest answer is no projection at all. | A | done |
