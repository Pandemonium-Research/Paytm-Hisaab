## Data and time

Use `sim_now(connection)` for every cutoff. `POST /sim/clock` permits rewinding; do not leak a
future case, pack, decision, escalation or delivery after rewind. Case rows come from
`ops.cases`; 6.9 stores freeze facts under `data.lien` and opens one case per lien. Only
`freeze`/`notice` belong in these contracted surfaces. Unknown merchants/cases return 404;
valid merchants with no cases return an empty list.

`record_pack` in `app/cases/packs.py` records `ops.packs` and a `pack.built` entry; the row's
`data.entry_seq` identifies that entry. The ledger payload carries `tier_totals` as
`dict[EvidenceTier, TierTotal]`, serialized with keys `"1"` through `"4"`. Tier 3 (ANSWER)
and tier 4 (AFTER_NOTICE) are weak. Weak share is their **amount** divided by all tier amounts;
return 0 for no pack or a zero total. Do not call the unbuilt `/skills/tiers` fixture.

Select the latest pack visible at the cutoff for each case, with deterministic tie handling
(ledger chain index for equal build times). Retain every sent pack in the outbox, including
older packs when a newer pack exists. Both pack build and decision/send evidence must belong
to the case's merchant and selected pack.

## Status and routes

`GET /app/cases?merchant=...`: real MerchantCaseRow items, newest case first with deterministic
case-ID ties. Show dispute amount and formatted rupees from the stored lien; notices may have
no disputed amount. Use plain titles such as "Payments on hold" and "Tax notice received".

`GET /app/officer/queue`: pending review cases across merchants with real business names,
dispute amounts, weak share and visible escalation reasons. Exclude cases whose latest visible
pack is already approved/rejected/sent. Unbuilt and awaiting-approval cases remain visible.
Escalation data, if used, must name the matching case and have a business timestamp at/before
the cutoff (`data.sim_at`, otherwise `created_at`). Never invent escalation findings.

`GET /app/officer/cases/{id}`: same OfficerQueueRow data plus selected pack ID, status,
chronological timeline, formatted tier totals, chain_ok and pdf_url. The statuses WF20 needs are:

- `open` before a pack exists;
- `awaiting_approval` once the pack is built and no decision is visible;
- `approved`/`rejected` from the pack's officer-role ledger entries at the cutoff;
- `sent` after the matching officer-role `pack.sent` evidence;
- `escalated` only when an actual visible escalation exists and there is no final decision.

Derive these from ledger evidence at the cutoff, not the mutable/latest `ops.approvals.status`.
This is required both for rewind and for consistency with 6.10's send gate. A rejection must
not be reported as approved/sent if conflicting evidence ever exists. Full chain verification
per detail request is intentional: call the existing `verify`, do not cache its result. An
unknown/future case must be rejected before verifying. Timeline is business time in IST;
include real rejection reasons/decision notes where present. Never return a placeholder PDF
URL; return null until a persisted artifact path exists. Future 6.8 may save a same-origin
`/api/packs/...` path in pack metadata.

`GET /app/officer/outbox`: join real simulated sends to their own pack/case/merchant and ledger
evidence. Use the send's ledger `sim_at` rather than `ops.outbox.sent_at` (wall time). Return
real freeze/build/approval/send instants and nonnegative integer elapsed seconds. Outcomes
remain null until actually recorded; do not claim a bank released/narrowed a hold. For the
current entire-account freeze, usable balance is 0 absent recorded release evidence; do not
copy the fixture's fabricated post-release balance. Never expose an unsent pack, a future
send, or another pack's approval. Sort newest sends first with deterministic ties.
