I want to think about how to create the synthetic data portion (section 6)

Yes. The key is **not to make “random fake transactions.”** Section 6 is actually one of the strongest parts of the plan because the synthetic generator should create a *known world* in which the classifier has to recover hidden provenance. The plan explicitly wants ground truth across all eight tags, seasonality, several merchant archetypes, a ₹40L threshold event, and a fraud-linked credit three layers downstream. 

I’d design it as a **generative simulation**, not a CSV faker.

### The basic idea

Have a hidden transaction-generation process:

```text
Merchant profile
      ↓
Business calendar / seasonality
      ↓
Generate genuine business activity
      ↓
Generate non-business activity
      ↓
Generate anomalies / duplicates / refunds
      ↓
Generate fraud propagation chain
      ↓
Visible transaction ledger
      +
Hidden ground-truth label
```

The classifier **never sees the hidden generation variables**. It only sees the signals that a real Paytm merchant system could plausibly have.

For example:

```text
Transaction
────────────────────────────────
txn_id             TXN_008421
timestamp          2026-03-14 11:42
amount             ₹1,250
payer_vpa          ravi@upi
payer_identifier   PAYER_481
merchant_id        M_003
channel            QR
terminal           QR_01
description        -
```

Ground truth, kept separately:

```text
txn_id             TXN_008421
true_label         taxable_supply
generation_reason  normal_customer_purchase
```

That separation is **very important**. Otherwise you accidentally leak the answer into the features.

## I would create 5 merchant archetypes

The plan currently specifies three types plus special cases. I'd make them slightly more explicit:

| Merchant                                   | Purpose                                       |
| ------------------------------------------ | --------------------------------------------- |
| **M1 — Exempt vegetable/grocery merchant** | Tests `exempt_supply` vs taxable              |
| **M2 — Mixed merchant**                    | Tests genuine mixture of taxable/exempt sales |
| **M3 — Family-account merchant**           | Tests `personal_transfer` / `inter_account`   |
| **M4 — Growing taxable merchant**          | Tests threshold projection                    |
| **M5 — Fraud-exposed merchant**            | Tests disputed-credit isolation               |

You don't necessarily need five completely independent merchants. They can overlap. In fact, I'd make **M4 also M3**, because that produces a much more realistic ledger.

# 1. Generate the "normal" customer transactions first

This should be the bulk of the data.

For each merchant define:

```python
merchant = {
    "business_type": "mixed_grocery",
    "avg_daily_transactions": 120,
    "avg_ticket": 480,
    "business_hours": (8, 21),
    "weekday_multiplier": ...,
    "weekend_multiplier": ...,
    "seasonality": ...,
}
```

Then generate transactions from distributions.

For example:

### Time

Don't simply choose a random timestamp.

Create an hourly probability distribution:

```text
00-06    0.5%
06-08    3%
08-10    10%
10-12    15%
12-14    18%
14-16    10%
16-18    15%
18-20    20%
20-22    8%
22-24    0.5%
```

Then introduce day-of-week effects.

That gives you the seasonality requirement in §6 rather than just claiming it exists.

### Amount

Use a log-normal or mixture distribution rather than uniform random amounts.

For example:

```text
small purchase       ₹50–₹300
normal purchase      ₹300–₹1,500
large purchase       ₹1,500–₹5,000
occasional bulk      ₹5,000–₹20,000
```

This creates realistic clusters.

# 2. Then inject the eight provenance classes

This is where I think the generator becomes interesting.

Don't generate the eight categories with equal probability.

Something like:

```text
taxable_supply       65%
exempt_supply        18%
personal_transfer     5%
refund_reversal       4%
duplicate             2%
inter_account         2%
non_business          3%
unclassified*         1%
```

But **`unclassified` should probably not actually be generated as a transaction type**.

That's an important distinction.

`unclassified` is supposed to mean:

> "The evidence available to the agent isn't sufficient."

So ground truth should contain the seven *real* provenance causes, while the classifier is allowed to output `unclassified`.

That lets you measure:

```text
accuracy
precision/recall
unclassified rate
false-confidence rate
```

rather than teaching the model that some transactions are intrinsically "unclassified."

# 3. Make each label have behavioral signatures

This is the most important part.

If the labels are generated randomly, the classification problem is meaningless.

### `taxable_supply`

Generate:

* recurring customer VPAs
* business-hour concentration
* ordinary purchase amounts
* repeated customer behavior
* higher frequency during peaks

Example:

```text
09:42  ₹420   customer_A
10:13  ₹780   customer_B
10:31  ₹260   customer_A
11:04  ₹1,240 customer_C
```

### `exempt_supply`

For the grocery/vegetable merchant:

```text
₹180
₹240
₹320
₹450
₹190
```

with perhaps different customer/amount distributions.

If POS/item-line information exists in your eventual sandbox, you can give these transactions:

```text
items = ["tomato", "potato", "onion"]
```

But **don't make this a dependency** because §8 explicitly identifies item-line/HSN availability as something to verify.

# 4. Personal transfers should be particularly interesting

This is where your classifier should *struggle*.

Suppose:

```text
₹15,000
Sunday
23:04
payer = savings-account-VPA
```

That's exactly the sort of example your demo already describes. 

Generate patterns like:

```text
₹15,000 from spouse
₹8,000 from own savings account
₹25,000 from sibling
₹12,000 from same payer every month
```

But don't make them *too* obvious.

For example:

```text
₹7,500 from spouse on Tuesday at 13:20
```

is deliberately ambiguous.

That's what should trigger:

> "I think this is a personal transfer because the payer has historically transferred money to you, but I'm not sufficiently confident. Confirm?"

That directly supports the plan's **agent proposes → merchant attests** architecture. 

---

# 5. Duplicates need relationships

Don't generate:

```text
duplicate = random transaction
```

Instead:

```text
TXN_1001  ₹850  12:41
TXN_1002  ₹850  12:42
```

Same:

* payer
* amount
* merchant
* item/order reference if available

Then perhaps:

```text
TXN_1002 → refunded at 12:48
```

The ground-truth relationship is:

```text
TXN_1001 = taxable_supply
TXN_1002 = duplicate
```

Now your classifier can actually use temporal/relational evidence.

---

# 6. Refunds should also be relational

Generate an earlier outgoing/incoming relationship:

```text
SALE
10:21 ₹2,400

REFUND
14:07 ₹2,400
```

The refund isn't itself a business sale.

Ground truth:

```text
refund_reversal
```

This also gives the evidence engine something useful to trace.

# 7. `inter_account` should have an account graph

This is where I'd make the synthetic dataset more sophisticated.

Instead of merely adding:

```text
₹20,000 → merchant
```

define:

```text
merchant_current
merchant_savings
merchant_business
family_account
```

and generate transfers:

```text
merchant_savings
       ↓
merchant_current
       ↓
Paytm merchant account
```

Ground truth:

```text
inter_account
```

Now you're effectively generating a tiny financial graph.

# 8. The fraud scenario should be a graph, not a special transaction

This is probably the coolest part of §6.

You want:

> "One credit seeded as fraud-linked, three layers downstream of a victim." 

I'd explicitly model:

```text
Victim
  │
  │ ₹50,000
  ▼
Account A
  │
  │ ₹20,000
  ▼
Account B
  │
  │ ₹4,200
  ▼
Merchant
```

The merchant sees:

```text
₹4,200 from Account B
```

They **do not know** it originated from the victim.

Your synthetic generator knows:

```text
fraud_chain_id = FC_001
layer = 3
victim_txn = TXN_001
```

This lets Module C test:

```text
340 credits
       ↓
isolate ₹4,200
       ↓
match sale
       ↓
produce evidence
```

rather than merely displaying a pre-selected fake fraudulent transaction.

# 9. The ₹40 lakh threshold should emerge naturally

I would **not** simply create:

```text
merchant.turnover = 4,000,001
```

Instead create a merchant whose activity grows.

For example:

```text
Jan     ₹2.4L
Feb     ₹2.7L
Mar     ₹3.0L
Apr     ₹3.2L
...
```

Then eventually:

```text
Mar 14
        cumulative taxable turnover
                 ↓
              ₹40L+
```

The deterministic skill calculates the crossing date.

This is much stronger because your demo can genuinely say:

> "Based on the transaction history, the projected threshold breach is March 14."

And the number is produced by the system rather than hardcoded. The plan specifically calls for threshold projection and a warning before the breach.

Small, deterministic, hand-controlled:

2. threshold breach

This separation is important.

Otherwise you risk building a dataset that your classifier performs amazingly on because you subconsciously designed the generator around the classifier.

## One architectural principle I'd enforce

**The generator should not know anything about the classifier.**

Instead:

```text
              GENERATOR
                  │
          hidden ground truth
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
 visible ledger        evaluation truth
        │
        ▼
   PROVENANCE AGENT
        │
        ▼
 proposed labels
        │
        ▼
     evaluator
        │
        └──────► accuracy / recall /
                  unclassified /
                  false confidence
```

That makes §6 a genuine experimental setup rather than demo scaffolding.

And it aligns extremely well with the plan's broader principle that the classifier should **refuse to guess when evidence is thin**; the plan explicitly says `unclassified` is preferable to a confident wrong classification. 

### My recommended next step

Before writing the generator, I'd define a **formal transaction schema + generation rules for each of the 7 ground-truth provenance classes**, including what signals are visible to the agent and what correlations are intentionally hidden.

That is the part worth getting right first. Once that is nailed down, the actual Python generator is probably only a couple hundred lines.
